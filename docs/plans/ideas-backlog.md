## New findings

Each with its evidence; the ideas below refer to them.

1. **Third-party request logs dominate the log.** `configure_logging` sets every stdlib logger to the app's level (`infrastructure/logging/setup.py`, the loop over `loggerDict`), so httpx's INFO line per request is written too: 48 % of production's log lines, each with the full URL, including CDN tokens that the app's own access log masks since 577e7cd. On the Pi the log lives on the SD card.
2. **The stream's own quality and size are read and thrown away.** `check_playable` (`hoster_resolvers/_verify.py`) fetches the first KiB of every resolved stream with a `Range` header: for HLS that is the master playlist with its `#EXT-X-STREAM-INF … RESOLUTION=1920x1080` lines, for a file the `Content-Range` header carries the total size. Neither is kept: no resolver sets a `StreamQuality` other than `UNKNOWN` (none of the 33 resolver modules), and `stream_builder` takes the quality from the plugin result alone (release name, site badge, link label). Streaming sites without release names therefore show no quality line in Stremio and rank as unknown.
3. **Hosters without a resolver are a blind spot.** A link whose hoster has no resolver is probed with `HEAD` (`HosterResolverRegistry._probe`, telemetry label `direct`); in 6 h all 81 probes were dead (plus 54 cached dead answers), i.e. embed pages. The hoster's name is logged at DEBUG only (`hoster_probe_*`), so neither the logs nor the metrics say which hosters the plugins deliver that nobody resolves, or which plugin emits them.
4. **No build identity in production.** The build-info metric carries the package version only, and the health routes report none; production runs `staging` (which commit is unknown without a shell). Every production measurement since 2026-10-03 had to infer the commit from behaviour.
5. **kinox costs without yield.** 35 searches, 0 results, 3.6 s and 6–14 requests with 503 retries each, every link-out behind the site's verification wall (KNOWN_ISSUES). The health check does not catch it (the site answers), the breaker does not either (an empty answer neither counts nor resets; option 2 in optimization-options.md).
6. **The deployment pipeline is hand-made.** The Pi builds the image from GitHub with its own Dockerfile (not in the repository; a copy in `.cache/live/pi/Dockerfile`), ships the plugins inside the image while `docker-compose.yml` mounts them, seeds `config.yaml` once (the February config ran for days, see [stremio-latency.md](stremio-latency.md)), and watchtower cannot update a locally built image. Each production test round began with "please rebuild".

### Task specifications for the items without an OpenSpec change

**I1 — third-party loggers.** In `configure_logging` (`infrastructure/logging/setup.py`), after the loop that sets every stdlib logger to the app's level, set `httpx` and `httpcore` to `WARNING` unless the app's level is `DEBUG` (then they keep it: the request trace stays available). Test: `tests/unit/infrastructure/test_logging*.py` asserts the levels for INFO and DEBUG configurations. Docs: the logging section of `docs/features/configuration.md` (one sentence), CHANGELOG. Acceptance: with `log_level: INFO`, no `"logger": "httpx"` lines in a run that fetches a page. `scripts/stremio_profile.py` counts the requests per host from these `HTTP Request:` lines: in the same commit, say in its docstring and in pi-performance.md ("How to re-measure") that the count needs `logging.level: DEBUG`, or count another way.

**I4 — build identity.** `infrastructure/version.py` gains `APP_COMMIT` and `APP_BUILT` from `SCAVENGARR_COMMIT` / `SCAVENGARR_BUILT` (default `unknown`). `Dockerfile.prod`: `ARG SCAVENGARR_COMMIT=unknown`, `ARG SCAVENGARR_BUILT=unknown`, exported as `ENV`; `docker-compose.yml` passes them (`build.args`), the image workflow of I7 passes `github.sha` and the build time. `scavengarr_build_info` carries `commit` and `built` beside `version` (one series; the values are not a label set in the sense of the telemetry rule, since the family has one series by construction). `/api/v1/healthz` and `/api/v1/stremio/health` report `version`, `commit`, `built`; the startup log has one `app_started` event with the three. Tests: the build-info collector test, the health route tests. Docs: `docs/features/observability.md` (build info), deployment notes. Acceptance: `prodctl.py metrics | grep build_info` shows the commit production runs.

**I9 — config drift guard.** Two startup events in the config loading path (`infrastructure/config/`, logged from `composition.py` where the config is applied):
- `config_effective`: the dotted paths and values of every field that differs from the schema default (`AppConfig()`), nested; secret fields (`SecretStr`, and any field whose name contains `password`, `token`, `key`, `secret`) are shown as `***`; dict-typed fields (`plugins.overrides`) as their key list. Also the config file path and whether a file was found.
- `config_unknown_keys` (WARNING): the dotted paths in the YAML that no schema field accepts. Known keys: the sections and top-level keys `_normalize_layer` (`infrastructure/config/load.py`) keeps, each nested model's fields and aliases (`cache.dir` is `CacheConfig.directory`), and the `AliasPath` aliases of `AppConfig`'s flat fields (`http`, `playwright` and `logging` have no nested model); skip dict-typed fields. Today `_normalize_layer` drops unknown top-level keys and pydantic ignores unknown nested ones, both silently. The config loads before logging is configured (`interfaces/cli/__main__.py`), so the loader collects the unknown keys and they are logged once logging is up.
Tests: a config with three non-defaults and one unknown key; a secret stays masked; the shipped `data/config.yaml` gives no warning. Docs: `docs/features/configuration.md` ("What the server logs at startup"). Acceptance: `prodctl.py logs --grep config_effective` answers "what does production run with?".

**I16 — OpenSpec hygiene.** `openspec archive add-config-system --skip-specs --yes` and `openspec archive add-plugin-loader --skip-specs --yes` (both untouched since January; `add-observability` is archived after the release that shipped it, v0.3.0), then `openspec validate --strict --no-interactive`. The OpenSpec row of next-steps.md §6 already records the decision to keep OpenSpec. One commit `chore(openspec): archive the two stale changes`.

**I3 — unknown-hoster inventory.** The fallback at the end of `HosterResolverRegistry.resolve()` (step 4: no resolver claims the URL; it calls `_probe`, the `direct` path) logs `hoster_without_resolver` at INFO with the hoster name (the URL's domain; never the URL) and counts it in a `Counter` the registry exposes (`unresolved_hosts()`, top 20). `/api/v1/stats/metrics` adds `"unresolved_hosters": {"<domain>": n}` from it (JSON only: the set of names is open, so it is no Prometheus label). Playlist URLs go through `_probe` too (moflix's own HLS playlists need no resolver); they are not counted. Tests: registry unit test (two probes, one domain twice; a playlist URL is not counted), stats route test. Docs: `docs/features/observability.md` (the JSON endpoint's fields), `hoster-resolvers.md` ("which resolver next": read this field). Acceptance: after a day, the field names the hosters the plugins deliver without a resolver, in order.

Rules, each with `for` and a one-line annotation: `ScavengarrDown` (target absent 5 min); `ScavengarrPluginWithoutYield` (a plugin with `plugin_search_total{outcome="hits"}` unchanged for 24 h while at least five plugins had hits); `ScavengarrSlowFirstAnswers` (`stremio_request_seconds` p50 for `source="search"` above 20 s over 1 h); `ScavengarrHosterBreakerOpen` (`circuit_breaker_open{breaker="hoster"}` for 6 h); `ScavengarrEventLoopLag` (p99 above 100 ms for 15 min); `ScavengarrNoStreams` (`stremio_request_total{outcome="empty"}` rate above half of all requests for 1 h).
