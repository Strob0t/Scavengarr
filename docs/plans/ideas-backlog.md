## New findings

Each with its evidence; the ideas below refer to them.

1. **Third-party request logs dominate the log.** `configure_logging` sets every stdlib logger to the app's level (`infrastructure/logging/setup.py`, the loop over `loggerDict`), so httpx's INFO line per request is written too: 48 % of production's log lines, each with the full URL, including CDN tokens that the app's own access log masks since 577e7cd. On the Pi the log lives on the SD card.
2. **The stream's own quality and size are read and thrown away.** `check_playable` (`hoster_resolvers/_verify.py`) fetches the first KiB of every resolved stream with a `Range` header: for HLS that is the master playlist with its `#EXT-X-STREAM-INF … RESOLUTION=1920x1080` lines, for a file the `Content-Range` header carries the total size. Neither is kept: no resolver sets a `StreamQuality` other than `UNKNOWN` (none of the 33 resolver modules), and `stream_builder` takes the quality from the plugin result alone (release name, site badge, link label). Streaming sites without release names therefore show no quality line in Stremio and rank as unknown.
3. **Hosters without a resolver are a blind spot.** A link whose hoster has no resolver is probed with `HEAD` (`HosterResolverRegistry._probe`, telemetry label `direct`); in 6 h all 81 probes were dead (plus 54 cached dead answers), i.e. embed pages. The hoster's name is logged at DEBUG only (`hoster_probe_*`), so neither the logs nor the metrics say which hosters the plugins deliver that nobody resolves, or which plugin emits them.
4. **No build identity in production.** The build-info metric carries the package version only, and the health routes report none; production runs `staging` (which commit is unknown without a shell). Every production measurement since 2026-10-03 had to infer the commit from behaviour.
5. **kinox costs without yield.** 35 searches, 0 results, 3.6 s and 6–14 requests with 503 retries each, every link-out behind the site's verification wall (KNOWN_ISSUES). The health check does not catch it (the site answers), the breaker does not either (an empty answer neither counts nor resets; option 2 in optimization-options.md).
6. **The deployment pipeline is hand-made.** The Pi builds the image from GitHub with its own Dockerfile (not in the repository; a copy in `.cache/live/pi/Dockerfile`), ships the plugins inside the image while `docker-compose.yml` mounts them, seeds `config.yaml` once (the February config ran for days, see [stremio-latency.md](stremio-latency.md)), and watchtower cannot update a locally built image. Each production test round began with "please rebuild".

## Handoff to the implementing agent

### Working rules

- **Two agents, one `staging`.** Before touching `application/use_cases/stremio_*.py`, `application/stremio/*`, `infrastructure/hoster_resolvers/*` or `plugins/*`, check that no other worktree has uncommitted changes there: `git worktree list`, then `git -C <worktree> status --short`. `git fetch` and rebase before every push; CHANGELOG conflicts keep both sides.
- **Release only in a quiet moment:** every worktree clean and pushed, CI green; otherwise in-flight CHANGELOG lines land under the wrong version.
- Each item: TDD, pre-commit and the full suite (AGENTS.md §1 and §6), docs in the same commit (CHANGELOG, the feature doc named below), one commit per item.
- OpenSpec changes (`openspec/changes/<id>/`) follow Stage 2 of `openspec/AGENTS.md`: read proposal, design and tasks, implement in order, tick the tasks, archive after the release that ships them.

### Orchestration (2026-10-07)

The advisor session (Mr. Fable) plans and dispatches; two coding sessions build, chosen by difficulty and scope. **Ultracode**: new capabilities, cross-layer work (use cases, ports, DI wiring), the stream and proxy path, resolvers and plugins with site analysis, anything with an OpenSpec change, defects without a known cause. **Mr. Normal**: fully specified single-area work: scripts and probes, docs, configuration files, tests from a precise spec, mechanical refactors, isolated fixes with a known cause. The rules that keep them apart:

- One step per session at a time, in its own worktree `handoff-<step>` branched from `origin/staging` (EnterWorktree bases on `origin/main`: `git fetch origin && git checkout -B handoff-<step> origin/staging` first), removed after the merge.
- A step's files are the ones its Order row and task specification name; the two active steps never share a code file. A step that needs another file asks the advisor first (SendMessage to Mr. Fable). Shared docs: `CHANGELOG.md` (one entry per step under the unreleased heading), `AGENTS.md` (only the sentence the step names), this file (only the step's own Order row); rebase before every push, keep both sides on a conflict.
- Dev servers: Ultracode on port 7979, Mr. Normal on 7981. Production stays read-only through `scripts/prodctl.py`, within its budget.
- After each push: `gh run watch <id> --exit-status`, a red run is fixed before anything else, then a report to Mr. Fable (shas, files, open points). Never `main`, never a force-push, never a merge.

### Findings

7. **Stutter is a per-connection limit.** FireStream's CDN throttles each connection to 1.5–3.9 Mbit/s while the stream needs about 2.9, and the browser player fetches segments one after another over one connection, through the proxy and directly alike (KNOWN_ISSUES, measured 2026-10-06). The proxy streams each segment as it arrives (`stream_hls_segment`) and fetches nothing ahead.
8. **Every production round is hand-made.** Six end-to-end rounds and the round-1 snapshot came from `prodctl.py metrics` and `logs` read by hand, dozens of Portainer requests each; `stremio_profile.py` measures requests and `stremio_playcheck.py` playability, and nothing joins them into the round's table.
9. **A worktree cannot run the full check.** The basedpyright hook (`entry: poetry run basedpyright`, `language: system`) runs in a worktree without `.venv`: Poetry creates an empty one and the hook ends with "Command not found" (twice on 2026-10-06); `poetry run pytest` fails the same way. **N1 — HLS read-ahead (decided 2026-10-07: measure first, then A or B; the probe measures both at once as well, so C rests on the same numbers).** The options discussed: (A) *read-ahead in the proxy*: a per-playlist `SegmentReadAhead` (`infrastructure/stremio/hls_proxy.py`) remembers the last media playlist it rewrote (the segment order) and, when segment *n* is requested, starts fetching *n+1* and *n+2* into memory (each at most 16 MiB, two per playback, a playback dropped 60 s after its last request, at most 8 playbacks); a request for a segment in the cache is served from it; concurrency under `_CDN_SEMAPHORE`; metrics `scavengarr_hls_readahead_total{outcome="hit"|"miss"|"dropped"}`. Doubles to triples the throughput of a sequential player on a per-connection limit (two to three connections in flight). (B) *parallel byte ranges*: when the CDN answers `Accept-Ranges: bytes` and the segment's `Content-Length` exceeds 1 MiB, fetch it in 2–3 ranges at once and forward them in order; no memory beyond the ranges in flight and no playlist knowledge needed, but a first range per segment before the rest can start, and nothing gained on CDNs that ignore ranges. (C) both. (D) nothing: the stutter stays documented as a client-side limit. Before the choice, measure: `scripts/probes/hls_throughput.py` fetches 10 segments of the FireStream title from the Pi sequentially, then with read-ahead 2, then in 3 ranges, then both at once (read-ahead 2 with each segment in 3 ranges: up to 9 connections), and prints Mbit/s for each run, the title's bitrate (segment bytes × 8 over their `EXTINF` durations) and whether the CDN honoured the ranges (`206` with `Content-Range`, not `200` with the whole segment), so the choice rests on the CDN's actual behaviour. Reading the numbers: a stutter-free playback needs *n* = ⌈1.5 × bitrate ÷ one connection's Mbit/s⌉ connections. *n* ≤ 3: one method alone, the faster run (A when they tie: it adds no requests and needs no range support; B when the first segment and seeks matter, as read-ahead helps neither). *n* > 3: C, both at once, and only while the combined run still scales (about three times the single-method runs); when it does not, the CDN caps per address or per session, no proxy-side trick reaches the bitrate, and D stays. For the FireStream title of finding 7 (2.9 Mbit/s against 1.5–3.9 per connection) *n* is 2–3: one method suffices, and C would open nine connections per viewer for nothing. C is for high-bitrate titles on a tightly throttled CDN; its nine connections per viewer share `_CDN_SEMAPHORE` (50) with every other playback, five viewers fill it. Risks: CDN rate limits (on 429 read-ahead turns off for that host for 10 min), memory (bounded), the `_CDN_SEMAPHORE` shared with other playbacks.
